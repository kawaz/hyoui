## 裁定待ち

### 👺NB-Q4: 固まった daemon の検出をどこまで入れるか

DR-0037 「固まった daemon の検出」節の 3 層。統括推しは c (1 は list-prune で実装中、2 は原因究明に必須、3 は有界な占有の可視化で安い)。

- [ ] a: 1 (CLI 側の stale / hung / live 分類) のみ
- [ ] b: 1 + 2 (daemon 内 watchdog がループ停滞をログ)
- [ ] c: 1 + 2 + 3 (status に直近 1 周の最大所要時間と最終周回からの経過も載せる)

### 👺NB-Q7: reap できない子を置いて daemon が終わる時の exit code

[DR-0037](decisions/DR-0037-daemon-nonblocking-event-loop.md) Q4。SIGKILL を送っても deadline までに reap できない子 (D state 等) を置いて daemon が終了する時、exit code を何にするか。統括推しは b (`128 + 9` は「子が SIGKILL で死んだ」と読めるが、実際には死を見届けていない。区別できないと、子が残っていることに気づけない)。

- [ ] a: 現行どおり `128 + 9`
- [ ] b: 別の値で区別する (値は実装時に、既存の exit code と重ならないものを選ぶ)

### 👺NB-Q8: fs が応答せず戻らない IO worker の扱い

DR-0037 Q6。record 等の fs への書き込みを担う worker thread が、fs の応答待ちで戻らない時にどうするか。統括推しは c (thread が際限なく増えるのを防ぎ、利用者には record が止まっていることが見える)。

- [ ] a: worker thread の上限を設け、上限に達したら `record.start` を拒否する
- [ ] b: その record を aborted として表示するだけ
- [ ] c: a と b の両方

### 👺NB-Q9: PTY 書き込みの失敗の意味論と、完了前に来た同じ client の入力

DR-0037 Q7。「PTY 書き込み effect の完了と失敗」節の 5 点 (書き残しの破棄、後続の effect を書かずに破棄、draining の期限 200ms、超過時に client が ack でなく EOF を見る) をこのまま確定してよいか。あわせて、同じ client の入力が前の書き込みの完了前に来た時、queue に積むか拒否するか。正規の client は ack を待ってから次を送るので、起きるのは ack を待たない外部 client だけ。統括推しは a と、後半は「積む」(拒否すると、外部 client の連続入力が途中で欠ける)。

- [ ] a: 5 点をこのまま確定し、完了前に来た入力は queue に積む
- [ ] b: 5 点をこのまま確定し、完了前に来た入力は拒否する
- [ ] c: 5 点を見直す (どこを変えたいかを書く)
