# vt100 crate PoC レポート (DR-0013)

実施日: 2026-05-27
対象: vt100 0.16.2
目的: screen emulator crate 比較 (`docs/research/2026-05-27-screen-emulator-crate-comparison.md`) で最有力候補となった vt100 について、残された懸念点 (serde 不在 / reflow 品質 / 実用 API 過不足) を実コードで検証する。

## 結論先出し

**判定: 条件付き GO (= reflow 品質を捨てて attach 復元中心の運用に振り切るなら採用可)。**

主要根拠 (5 行):
1. `state_formatted()` は **alt screen フラグを復元しない** → hyoui wrapper で先頭に `?1049h` を補う必要あり、ただし 1 行で済む
2. **`set_size()` の reflow は truncate のみで内容を保存しない** → wezterm-term/alacritty_terminal レベルではなく、resize を高頻度に通る用途には不向き
3. 画面内容・色・属性・wide char/grapheme/emoji の保持は **完全に機能** (= 復元品質は cell-level で問題なし)
4. `state_formatted()` は 100KB feed 後でも 15us (release) と非常に高速、運用負荷ゼロ
5. CBOR snapshot wrapper は 121 行で実装可能、roundtrip OK。ただし bytes 量が `state_formatted` の **283 倍** に膨らむため運用上は `state_formatted` 優先で十分

resize/reflow を諦められない場合は wezterm-term への切替を検討、ただしその場合 maintenance bus factor が改善する代わりに API が大きくなる。

## 各検証項目の結果

### 検証 1: 基本構築

- **判定: ✓**
- `vt100::Parser::new(rows, cols, scrollback_len)` で素直に構築できる
- API ergonomics: 良好。`Parser::process(&[u8])` / `Parser::screen() -> &Screen` の二段が分かりやすい
- **要注意挙動**: `\n` (LF 単体) は cursor の **row を進めるが col をリセットしない** (= raw mode 標準)。`\r\n` で次行頭に行く。PTY 出力は通常 `\r\n` を出すため実害なし

### 検証 2: state_formatted() の往復

- **判定: 部分的**
- シンプル ANSI (色付き文字 + `\r\n`): ✓ 完全 roundtrip (cell 内容・色・bold 全部一致)
- alt screen (`?1049h`) を含む入力: **✗ alt フラグが復元されない**
- formatted bytes の内訳:
  ```
  ESC[?25h ESC[m ESC[H ESC[J <content> ESC[5;10H@ ESC> ESC[?1l ESC[?2004l
  ```
  → cursor 表示状態 / 色リセット / Home / clear / 本体描画 / cursor 位置 / app keypad off / DECCKM off / bracketed paste off
- **alt screen 入退場 (`?1049h` / `?1049l`) が出力に含まれていない**
- 影響: claude TUI など alt screen 常駐アプリは復元後に primary screen で再描画される → hyoui 側で `screen.alternate_screen()` を読んで先頭に `\x1b[?1049h` を補う必要あり (= wrapper で 1 行)

### 検証 3: claude TUI 風 ANSI 入力

- **判定: 部分的 (= 内容は ✓、alt フラグのみ ✗)**
- box drawing (`┌─┐│└┘├┤`) + 色付き title + 部分 update (`\x1b[5;8H\x1b[7mUPDATED`) + 反転属性まで全て正しく cell 状態として保持
- state_formatted() の bytes (= 750 byte) で画面内容は完全復元
- 描画イメージ (実画面で再生したと想定):
  ```
  ┌────────────────────────────────────────┐
  │ Claude Code                              │
  ├────────────────────────────────────────┤
  │ line 00                                  │
  │ line UPDATED                             │  ← (5,8) に反転で挿入
  │ line 02                                  │
  ...
  └────────────────────────────────────────┘
  > typing...
  ```
- 復元側でも同一の見た目 (alt フラグだけは外側で補完必要)

### 検証 4: alternate screen 切替

- **判定: ✓**
- `\x1b[?1049h` → 描画 → `\x1b[?1049l` で primary 復帰
- primary の内容が完全保存される (alt 中の描画で上書きされない)
- `Screen::alternate_screen()` getter も正しく true/false を返す
- alt フラグの問題は **state_formatted() 出力** に限る話で、Parser 自体の振る舞いは正しい

### 検証 5: scrollback アクセス

- **判定: ✓ (ただし evicted age 系 API なし)**
- `Parser::new(rows, cols, scrollback_len)` で scrollback capacity 指定
- `Screen::set_scrollback(n)` / `Screen::scrollback() -> usize` で過去位置スクロール
- `Screen::contents() -> String` で表示中の viewport (scrollback offset 反映) を取得
- **`last_evicted_age` 相当 API は public に存在しない** → hyoui 既存仕様を継承するなら、Parser を包む wrapper で「累積 feed 行数」を自前 count する必要あり (= 数十行で実装可能)
- 50 行を 10 行画面 + scrollback 100 に流したテスト: 最終 viewport に line-041 〜 line-049 + 空 1 行が残るのを確認

### 検証 6: resize + reflow 品質 ← 最重点

- **判定: ✗ (truncate のみ、reflow なし)**
- 80 cols で 100 文字の行を流す: 80 文字目で wrap して 2 行になる (= 正しい)
- `set_size(24, 40)` で 40 cols に縮小:
  - 元 80 cols の行: 先頭 40 文字だけ残り、**残りの 40 文字は捨てられる**
  - wrap で続いていた 2 行目も同様に切り詰め
- `set_size(24, 80)` で 80 cols に戻す:
  - **失われた文字は復元されない** → 行内に空白が残る
- 観測ログ:
  ```
  initial 80x24:
    r00↵|ABCDEFGHIJKLMNOPQRSTUVWXYZABCDEFGHIJKLMNOPQRSTUVWXYZABCDEFGHIJKLMNOPQRSTUVWXYZAB|
    r01 |CDEFGHIJKLMNOPQRSTUV                                                            |

  after set_size(24, 40):
    r00 |ABCDEFGHIJKLMNOPQRSTUVWXYZABCDEFGHIJKLMN|  ← 40 文字で truncate
    r01 |CDEFGHIJKLMNOPQRSTUV                    |

  after set_size(24, 80):
    r00 |ABCDEFGHIJKLMNOPQRSTUVWXYZABCDEFGHIJKLMN                                        |  ← 復元せず
    r01 |CDEFGHIJKLMNOPQRSTUV                                                            |
  ```
- **結論**: vt100 の reflow は wezterm-term / alacritty_terminal レベルではない。`set_size` を高頻度に通す用途 (= ターミナルウィンドウの動的リサイズ追従) では情報損失が起きる
- 救済策候補:
  1. 「resize 前に state_formatted() を取って、resize 後に新 Parser を作って feed 直す」運用 (= alt screen 含めて hyoui wrapper で補完)
  2. resize を起こさない設計に倒す (= fixed-size virtual terminal として運用、size 変更時は新 Parser 作成)
  3. 諦めて wezterm-term に切替
- 救済策 1/2 が実用上は最も低コスト

### 検証 7: cursor / mode 状態

- **判定: ✓ (全 API 正常動作)**
- 検証した getter / setter:
  - `cursor_position() -> (u16, u16)`: 1-origin ANSI (`\x1b[5;10H`) を 0-origin (4, 9) に正しく変換
  - `hide_cursor()`: `\x1b[?25l` / `\x1b[?25h` で切替確認
  - `application_keypad()`: `\x1b=` / `\x1b>` で切替確認
  - `application_cursor()` (DECCKM): `\x1b[?1h` / `\x1b[?1l` で切替確認
  - `bracketed_paste()`: `\x1b[?2004h` / `\x1b[?2004l` で切替確認
  - `mouse_protocol_mode() -> MouseProtocolMode`: enum で `None` / `PressRelease` (1000) / `ButtonMotion` (1002) 等を返す
  - `mouse_protocol_encoding() -> MouseProtocolEncoding`: SGR/X10 等 enum
- API ergonomics: 良好。enum で型付きに取れるので分岐が書きやすい

### 検証 8: wide char / grapheme cluster

- **判定: ✓ (全パターン正常)**
- 日本語 (`あいうえお`): 各文字が `(row, col)` と `(row, col+1)` の 2 セルで保持、`is_wide()` / `is_wide_continuation()` フラグ OK、cursor 位置も 5 文字で col=10
- emoji (`🎉`): wide=true で 1 セルに保持
- combining char (`e\u{0301}`): **`Cell::contents()` で `"e\u{0301}"` を 1 セルに保持** → grapheme cluster ベースの実装が正しく機能している
- mixed (`Hi 日本 🎉 e\u{0301}!`): すべて期待通りの col 配置
- 結論: claude TUI が日本語混在で出してくる出力でも問題なし

### 検証 9: CBOR snapshot wrapper 試作

- **判定: ✓ (実装可能、ただしサイズ膨張に注意)**
- 実装ボリューム: `crates/poc-vt100/src/lib.rs` 全体で **121 行 / 非空白非コメント 96 行**
  - `ColorSnap` enum (4 行) + `From<vt100::Color>` impl (8 行)
  - `CellSnap` struct (12 行) + `From<&vt100::Cell>` impl (14 行) + `Default` impl (auto-derive)
  - `ScreenSnap` struct (12 行) + `from_screen` (18 行) + `to_cbor`/`from_cbor` (8 行)
- roundtrip テスト (`v09_cbor_roundtrip`): cell 内容・色 (`ColorSnap::Idx(1)`)・bold・hide_cursor まで完全保持
- 同一画面の bytes 比較:
  - `state_formatted()`: 568 bytes
  - CBOR snapshot: 161,066 bytes
  - **比率: 283 倍**
- 大きさの理由: 24x80 = 1920 セル × 1 セルあたり (String + 2 Color enum + 5 bool + 2 bool wide flags) を CBOR で素直に encode しているため
- 最適化候補: 空 cell スキップ、Color の variant 整数化、属性 bit pack、Cow<str>、`#[serde(skip_serializing_if = "is_default")]` 多用、RLE → 実用化時は適用必須
- ただし **hyoui の attach 復元 protocol では `state_formatted()` のほうが圧倒的に小さく速い** → CBOR snapshot wrapper は `state_formatted()` の補完 (= alt フラグ / mouse mode / scrollback 個別情報) を encode する小さな構造体にとどめ、本体は `state_formatted()` を使うのが最適と判断

### 検証 10: パフォーマンス感覚

- **判定: ✓ (十分高速)**
- 100KB の claude TUI 風 dump を feed:
  | 操作 | debug build | release build |
  |---|---|---|
  | `Parser::process(100KB)` | 12.01 ms | **0.60 ms** (= ~167 MB/s) |
  | `Screen::state_formatted()` | 114 us | **15 us** (= 1603 bytes 出力) |
  | `ScreenSnap::from_screen()` | 461 us | **50 us** |
  | `snap.to_cbor()` | 3.8 ms | **205 us** (= 162 KB CBOR) |
- 結論: PTY からの byte stream を捌くのに十分すぎる性能。1Hz の snapshot でも余裕、リアルタイム attach 通知でも CPU 食わない

## 採用 GO / NO-GO 最終判断

**判定: 条件付き GO**

GO 条件:
- ✅ Cell/Screen serde 不在は wrapper 96 行で解決可能
- ✅ state_formatted() の alt フラグ不在は 1 行の prepend wrapper で解決可能
- ✅ `last_evicted_age` 相当も外側で行数 count するだけで再現可能
- ✅ 画面内容・色・属性・wide char・grapheme は完全に保持される
- ✅ 性能は問題なし (release で 100KB feed 0.6ms)

NO-GO リスク:
- ❌ resize 時の reflow が truncate のみ → resize を高頻度に走らせる用途には不向き
  - 救済策あり: 「resize 時は新 Parser を作って raw bytes を feed 直す」運用に倒せば実用可能
- ⚠️ bus factor: 個人メンテ (PoC で潰せない、別途方針判断要)

**推奨運用方針**:
1. vt100 を採用し、Parser を hyoui 側の `VirtualScreen` で包む
2. resize は受けるが、`set_size` を呼ばず **新 Parser を作って入力ストリームを再 feed** する形に倒す (= reflow の代わりに完全な再構築)
3. attach 復元は `state_formatted()` + alt フラグ補完 + scrollback meta を CBOR で 1 つの bundle にする (= 既存 DR-0008 連動可)
4. 将来 bus factor 不安が顕在化した場合は wezterm-term への移行ルートを設計の表に残しておく

## 残懸念 (PoC で潰せなかったもの)

1. **bus factor (個人メンテ)**: PoC では検証不能。最終リリースから 2 年経過 (0.16.2 = 2024-01) の現状をどう評価するか別途判断。security advisory はなし
2. **入力履歴 buffer の容量設計**: resize 救済策で全 byte 履歴を保持する場合、claude TUI は数時間で MB 級になりうる。periodic に `state_formatted()` を取って **古い byte を捨てる** 設計が必要 → 別 DR
3. **DR-0008 (snapshot bundle 形式) との整合**: DR-0008 で snapshot 形式を決めた前提だが、本 PoC では具体の bundle protocol は試していない (= ScreenSnap wrapper の存在だけ確認)
4. **CBOR snapshot のサイズ最適化**: 283x 倍は実用にならないので、もし採用するなら空 cell スキップ + Color/Attrs bit pack + RLE で 1-2 桁削減が必要 (実装可能性は高い)
5. **claude TUI 実出力での real-world テスト**: PoC では合成された ANSI 入力のみ。実 claude セッションを `script` 等で録画してリプレイする検証は次フェーズ
