# ブラウザ側ターミナル描画器の調査 (2026-10-04)

## 調査範囲と前提

選定対象はブラウザの描画・入力面。自前描画案については、その前提となる daemon / gateway の変更量も評価する。daemon の screen state は Rust の vt100 crate が正本 ([DR-0013](../decisions/DR-0013-screen-emulator-and-attach-stability.md))。現行 web は xterm.js 5.3.0 と addon-fit 0.10.0 / addon-unicode11 0.8.0 / addon-web-links 0.9.0 を vendor し、classic script から使用する ([棚卸し](../findings/2026-10-03-web-component-tree.md))。以下の候補のバージョン・外部仕様は 2026-10-04 時点の一次資料で確認する。

[作り直しの合意](../issue/2026-10-04-design-webui-terminal-app-rework.md)に沿い、1 pane = 1 インスタンスの iframe ツリー、多数 pane、IME と iOS Safari / iPad PWA、アプリの DECSET マウス要求を変えない転送遮断、leader の cols/rows 固定の content-fit、OSC 8、選択とコピー、親 frame のソフトキーから postMessage での入力を評価する。既存の `term._core` 依存は公開 API ではないため移行時の再検証対象である。

## xterm.js 5.3.0 から 6.0.0 の具体的な変化

- [5.4.0](https://github.com/xtermjs/xterm.js/releases/tag/5.4.0) で旧 `xterm` / `xterm-*` npm パッケージは deprecated、新名 `@xterm/xterm` / `@xterm/addon-fit` / `@xterm/addon-unicode11` / `@xterm/addon-web-links`。同版で公開 `Terminal.input(data, wasUserInput?)`、`attachCustomWheelEventHandler`、`documentOverride` を追加した。ただし `input()` は既定で onData を発火させる「端末への入力」であり、親 frame からの入力を子の WS に直結する既存経路との意味の差は別途決める必要がある ([types](https://github.com/xtermjs/xterm.js/blob/6.0.0/typings/xterm.d.ts))。
- [5.5.0](https://github.com/xtermjs/xterm.js/releases/tag/5.5.0) は WebGL の重なる glyph の縮小オプションと DOM の描画改善。5.4.0 の release で DOM の selection 修正、WebGL の Safari 対応修正が列挙されるが、これらだけで iOS IME 成功は証明できない。
- [6.0.0](https://github.com/xtermjs/xterm.js/releases/tag/6.0.0) は ESM ビルド (`lib/xterm.mjs`)、DEC synchronized output、OSC52、OSC8 の URI セミコロン修正、特定 IME の二重入力修正、alt buffer・マウスオフ時のページスクロール修正。DOM fallback が標準、canvas addon は削除され WebGL addon が任意。viewport / scrollbar の実装変更、旧オプション削除も breaking と記載。
- `term._core._syncTextArea()`、`_compositionHelper.isComposing`、`_charSizeService.measure()`、Unicode provider 内部列挙は公開 `typings/xterm.d.ts` に存在しない。内部構造の更新差分と補正の必要性を移行時に検査する ([現行棚卸し](../findings/2026-10-03-web-component-tree.md)、[6.0.0 source](https://github.com/xtermjs/xterm.js/blob/6.0.0/src/browser/CoreBrowserTerminal.ts))。

以上の版・日付は GitHub Releases API と各 tag の source に対する 2026-10-04 の確認結果。npm registry に公開済みの `@xterm/xterm` 6.0.0 の [メタデータ](https://registry.npmjs.org/@xterm/xterm/6.0.0) と配布 tarball の `lib/xterm.mjs` も照合した。6.0.0 tag の package.json は `@xterm/addon-fit` 0.11.0、`@xterm/addon-unicode11` 0.9.0、`@xterm/addon-web-links` 0.12.0、任意の `@xterm/addon-webgl` 0.19.0 ([各 addon package.json](https://github.com/xtermjs/xterm.js/tree/6.0.0/addons))。公開 tarball の core と三つの addon の `.mjs` はそれぞれ自己完結した ESM 配布物であり、検査した四ファイルに `@xterm/*` の bare import はなかった。`<script type="module">` と相対パス import で vendor できる配布形式だが、iframe と実ブラウザでの読込成功は未確認。

## 深掘り A: iOS Safari / iPad PWA の IME

xterm.js 6.0.0 は補助 textarea を通常時は cursor cell へ [`_syncTextArea()`](https://github.com/xtermjs/xterm.js/blob/6.0.0/src/browser/CoreBrowserTerminal.ts#L301-L325) で移動し、変換中には [`CompositionHelper.updateCompositionElements()`](https://github.com/xtermjs/xterm.js/blob/6.0.0/src/browser/input/CompositionHelper.ts#L208-L245) が composition view と textarea の双方を同じ cursor cell に追従させる。確定時には textarea の値から送信する。`compositionend.data` だけに依存しないのはブラウザ間の差を吸収するため ([同 source](https://github.com/xtermjs/xterm.js/blob/6.0.0/src/browser/input/CompositionHelper.ts#L119-L175))。ただし現行 hyoui の 5.3.0 向けクリア・再同期・二重送信防止パッチは内部 API を呼ぶ ([棚卸し](../findings/2026-10-03-web-component-tree.md#74-モバイル-ime--safari--ios))。6.0.0 の内部実装が類似していることはパッチが不要・安全である証明ではない。

xterm.js の iOS 26 Safari / Chrome では中国語 IME のスペースと句読点が落ちる [master に対する未解決報告と実イベント順](https://github.com/xtermjs/xterm.js/issues/5835) があり（6.0.0 tag での再現は未確認）、6.0.0 の Chromium/Linux で負荷時の韓国語確定文字脱落 [未解決報告](https://github.com/xtermjs/xterm.js/issues/6089) もある。後者を iOS で再現すると断言はできない。macOS の特定 IME でも `input` が `keydown` に先行するケースの確定文字脱落 [報告](https://github.com/xtermjs/xterm.js/issues/6144) がある。評価対象は「変換中の UI が terminal cursor に付くか」と「確定時に欠落・重複なく onData に 1 回だけ届くか」を**独立した軸**にする。

ghostty-web 0.4.0 は `touchend` で textarea に focus し iOS 対応を [release](https://github.com/coder/ghostty-web/releases/tag/v0.4.0) に記載するが、textarea は `left:0/top:0`、透明かつ clip され、[`compositionupdate` は no-op](https://github.com/coder/ghostty-web/blob/v0.4.0/lib/input-handler.ts#L516-L557)。確定 `event.data` は送る一方、変換中の UI を cursor に追従させない。[改善 PR #190](https://github.com/coder/ghostty-web/pull/190) は未統合で、PR 自体もネイティブ Safari IME 未テストと明記する。[PR #90](https://github.com/coder/ghostty-web/pull/90) の日中 IME 対応は「初期実装」と明記されている。xterm.js / ghostty-web とも **iOS Safari 日本語 IME、iPad の standalone PWA、ソフトキーボード・iframe を掛け合わせた実機試験は未実施**。Safari の desktop エミュレーションで代替しない。

## 深掘り B: DECSET の保持とマウス転送だけの遮断

xterm.js 6.0.0 の公開 [`modes.mouseTrackingMode`](https://github.com/xtermjs/xterm.js/blob/6.0.0/typings/xterm.d.ts#L1905-L1932) は DECSET 要求を取得できる。[`CoreMouseService.triggerMouseEvent`](https://github.com/xtermjs/xterm.js/blob/6.0.0/src/common/services/CoreMouseService.ts#L280-L337) は active protocol で報告を生成し、従来 encoding は `onBinary`、SGR 等は `onData` に到達する。つまり **onData 全停止ではキー入力も失う**。マウス report らしい文字列を `onData` / `onBinary` で判別する方式は端末入力の同じ byte 列を誤判定しうるので、公開 API だけで転送だけを止める方法とは言えない。

ソースの [`onProtocolChange`](https://github.com/xtermjs/xterm.js/blob/6.0.0/src/browser/CoreBrowserTerminal.ts#L727-L774) はマウス要求が入ると selection service を `disable()`、要素へ mouse listeners を結線し、wheel の default action を cancel する。従って「送信 callback を止める」だけでは選択・縦スクロールが戻らない。公開 `macOptionClickForcesSelection` (Mac の Option) / 他環境の Shift は [強制選択のための修飾キー](https://github.com/xtermjs/xterm.js/blob/6.0.0/src/browser/services/SelectionService.ts#L433-L470)であり、pane の常時 off の代わりではない。公開 `attachCustomWheelEventHandler` は wheel だけ、`attachCustomKeyEventHandler` は key だけで、mouse down / move の任意停止 API ではない ([types](https://github.com/xtermjs/xterm.js/blob/6.0.0/typings/xterm.d.ts))。**今回の要件を満たす公式公開 toggle はソース・types で確認できない**。外側の capture listener で xterm のハンドラに届く前にイベントを止め、off 時の選択・touch・scroll は UI 側で用意する案は候補だが、実イベント経路の PoC 未検証で採用決定は不可。xterm の内部状態に直接書き込んで DECSET を偽装する案は透過原則に反する ([DR-0014](../decisions/DR-0014-transparency-and-empirical-verification.md))。

ghostty-web 0.4.0 には [`hasMouseTracking()`](https://github.com/coder/ghostty-web/blob/v0.4.0/lib/terminal.ts#L1823-L1827) があるが、[追跡 issue #104](https://github.com/coder/ghostty-web/issues/104) は click / motion / wheel の report 未実装を説明する（issue は 2026-08-12 に close、ただし **0.4.0 tag の source** に送信処理を確認できない）。報告する機能の不在は「転送のオン・オフを選択可能」の達成ではない。

## 深掘り C: 多インスタンスのメモリ・描画コスト

xterm.js は addon を載せなければ [DOM renderer](https://github.com/xtermjs/xterm.js/blob/6.0.0/src/browser/renderer/dom/DomRenderer.ts#L30)、WebGL addon は [terminal ごとに canvas の WebGL2 context を作る](https://github.com/xtermjs/xterm.js/blob/6.0.0/addons/addon-webgl/src/WebglRenderer.ts#L79-L110)。[addon の公式 README](https://github.com/xtermjs/xterm.js/blob/6.0.0/addons/addon-webgl/README.md#L26-L37) は OOM / suspend 等で context loss が起こるので `onContextLoss` を扱うよう案内する。[多数 pane の未解決 issue #4379](https://github.com/xtermjs/xterm.js/issues/4379) は 25 pane の例でブラウザ context 数が問題と報告、2026-09 の利用者コメントは「約 16 contexts」と経験値を述べる。**16 は標準化された上限ではなく環境依存の報告**。iframe に分ければ制限が解消すると判断する資料もない。WebGPU renderer [PR #6137](https://github.com/xtermjs/xterm.js/pull/6137) は 2026-10-04 時点で open のため選定候補の安定機能として数えない。

ghostty-web は Canvas 2D [`getContext('2d')`](https://github.com/coder/ghostty-web/blob/v0.4.0/lib/renderer.ts#L141-L155) なので pane ごとの WebGL context 上限は該当しない。一方で [terminal ごとの RAF loop](https://github.com/coder/ghostty-web/blob/v0.4.0/lib/terminal.ts#L1094-L1119) は dirty row がなくても `renderer.render()` を毎 frame 呼ぶ。Canvas は [CSS 寸法 × devicePixelRatio²](https://github.com/coder/ghostty-web/blob/v0.4.0/lib/renderer.ts#L234-L249) の backing store を各 pane に持ち、WASM terminal も pane ごと。xterm.js DOM 側も buffer / DOM / 各 iframe 自体の固定費があり、どちらが軽いかはこれらソースからは決められない。非表示タブ・カルーセル・複数 iframe の **pane 数 × 可視/不可視 × browser × renderer** で JS heap / GPU memory / FPS / frame time / context-loss を測る必要がある。

## 自前描画と中間案の実装境界

**自前描画はブラウザ側の VT parser をなくす設計案で、現行実装の機能名ではない。** daemon の [`ScreenState`](../../crates/hyoui/src/daemon/screen/state.rs) は vt100 で child bytes を解釈し、[`build_screen_snapshot`](../../crates/hyoui/src/daemon/screen/snapshot.rs) は sparse な visible cells、cursor、mode、grid、`current_seqno` を取り出せる。しかし [`RowCellSnap`](../../crates/hyoui/src/daemon/screen/state.rs) から [serialized `CellSnapshot`](../../crates/hyoui/src/daemon/screen/snapshot.rs) へ出るのは文字・太字 / 斜体 / 下線 / 反転・全角先頭だけで、foreground/background、dim / blink / strike、OSC 8 URI は渡らない。[`ModeSnap`](../../crates/hyoui/src/protocol/messages/screen.rs) に application cursor/keypad と bracketed paste はあるが、mouse mode / encoding はない。vt100 crate は `mouse_protocol_mode()` / `mouse_protocol_encoding()` を備える ([依存ソース](https://github.com/doy/vt100-rust/blob/v0.16.2/src/screen.rs)) が hyoui wrapper が公開していない。OSC 8 は crate の parser 自体が捨てる ([既知問題](../issue/2026-08-24-attach-osc8-hyperlink-metadata-loss.md)) ため snapshot に field を足すだけでは直らない。

現在の [`state-snapshot-v1`](../../crates/hyoui/src/protocol/messages/screen.rs) は daemon の要求 / 応答型。gateway は [WS の RAW_DATA だけを binary で browser に送り、対応外の daemon control を捨てる](../../crates/hyoui-web/src/ws_attach.rs)。browser から snapshot を取得する経路も、daemon に変更セルを通知・配信する API もない。`current_seqno` は [`process(bytes)` ごとに一度増えるだけ](../../crates/hyoui/src/daemon/screen/state.rs)で、dirty な行や cell の位置は保持しない。[DR-0013 の `DirtyLinesNotify` / `GetLines`](../decisions/DR-0013-screen-emulator-and-attach-stability.md) は設計案であり実装エビデンスはない。しかも DR の `GetLinesResponse` は `ansi_bytes` と定義されているため、その設計をそのまま実装しても **ブラウザに VT parser を置かないセル差分にはならない**。自前案には完全な cell 属性、必要な mode、行・cell 差分、初期状態と更新の順序保証、切断 / 遅延 / 欠落時の再同期、描画対象の scrollback を含む**新しい契約の設計と実装が必要**。mode はアプリの要求を観察・通知するだけで、子への DECSET を書き換えない。

自前案にはさらに、文字幅 / 合字 / 結合文字、選択ハイライトとコピー、OSC 8 の URI と安全な起動、cursor / blink、色 / 属性 / 画像の表示範囲、scrollback の有無と操作、問い合わせ応答、キーボード escape 変換、IME preedit と確定が必要になる。`StateSnapshotRequest` は visible grid の全量取得には利用できるが、[`SnapshotComponent::Scrollback` は要求時に error](../../crates/hyoui/src/daemon/control.rs) であり、別の [`screen.dump` CBOR / scrollback](../../crates/hyoui/src/daemon/screen/snapshot.rs) はあるものの web の連続表示契約ではない。全量を毎更新時に送ると unchanged cells まで複製する一方、差分は daemon 側の dirty 管理と基準 seqno を要する。転送 bytes 量・処理遅延が raw PTY より増減する条件は描画内容次第であり未計測。現行の daemon と xterm.js に**二つある VT parser の可視状態不一致をなくせる**可能性が利点だが、現在の daemon state が OSC 8 を含め完全であるとは言えず、この前提が達成されてからの利点である。

**中間案は xterm.js 6.0.0 が raw bytes を parse / render / IME / keyboard encode し続け、DOM の mouse と選択だけを hyoui 側が引き受ける案。** daemon 側を増やさず、[公開 `modes.mouseTrackingMode`](https://github.com/xtermjs/xterm.js/blob/6.0.0/typings/xterm.d.ts#L1905-L1932) を表示に使える。ただし [xterm の mouse handler は DECSET 中に自動で結線され selection service が disable](https://github.com/xtermjs/xterm.js/blob/6.0.0/src/browser/CoreBrowserTerminal.ts#L727-L804) される。capture listener がその handler を止めることと、ドラッグ選択・scroll・touch・IME focus・リンク操作を自前で復旧できることは別の問題。さらに xterm の [公開 buffer line / cell API](https://github.com/xtermjs/xterm.js/blob/6.0.0/typings/xterm.d.ts) を使って選択文字・全角幅・scrollback 座標を組み立てる範囲は要 PoC。xterm 内部の選択処理を私的 API で enable する想定はしない。中間案は browser の parser 二重化を残し、daemon の OSC 8 attach 復元欠落も解消しない。「二案の良いところを無条件に足せる」設計とは評価しない。

## xterm.js を続ける場合の移行コストと利得

1. **vendor と読み込み**: 5.3.0 の UMD `xterm.js` と既存 addon を 6.0.0 core / 対応 addon の `.mjs` と `xterm.css` に入れ替える。`session.html` の classic script 読み込みと `window.Terminal` 等を module import に変更する。公開 tarball 四点の import 依存検査は済み。ただし現行 [`content_type_for`](../../crates/hyoui-web/src/lib.rs) は `.mjs` を `application/octet-stream` として配信するため、module を読み込む前に JavaScript MIME を追加する必要がある。CSP・iframe 越し読み込みの実ブラウザ確認は未実施。addon-web-links は旧 `xterm-addon-web-links` 0.9.0 から scoped 0.12.0 へ変わる ([現行 vendor メモ](../../crates/hyoui-web/assets/vendor/README.md)、[新 tag](https://github.com/xtermjs/xterm.js/tree/6.0.0/addons/addon-web-links))。
2. **既存内部依存の再評価**: [`session.js`](../../crates/hyoui-web/assets/session.js) の `_core.unicodeService._providers` fallback、`_charSizeService.measure()`、`_syncTextArea()` / `_compositionHelper.isComposing` の各箇所について、削除できる補正は削除し、残す場合は 6.0.0 の source と日本語 IME・フォントロード時の実測で保証する。Unicode11 の公開 `term.unicode.register()` は維持、[`captureUnicode11()`](../../crates/hyoui-web/assets/unicode-ambiguous.js) は addon.activate の呼び出しで provider を取得するが、6.0.0 と組み合わせた検証は別に必要。新たな内部依存を根拠なく増やさない。
3. **入力・描画の移植**: `onData` + `onBinary` → WebSocket の byte 中継を保ち、`input()` と postMessage の使用経路を明確化する。特に OSC 8 の `linkHandler` と URL addon の双方、選択・コピー、旧 touch / Linkifier2 手順、IME の位置 / 確定 / 二重送信は回帰試験が必要。6.0.0 は viewport / scrollbar が breaking なので `fitAddon.proposeDimensions()` のみ使って leader と非 leader を分ける既存 resize 経路の再検証も要る。`fontSize` を変える content-fit は public API の範囲だが、実際の文字セル計測・cols/rows 保持・読みやすい下限は未計測。
4. **具体的な利得**: scoped package と自己完結 ESM で現行の読み込み順・グローバル共有を撤去可能。xterm の公開 `modes.mouseTrackingMode`、`input()`、wheel handler、多 window 対応を利用できる。6.0.0 の OSC 8 URI / IME 二重入力の修正、DOM selection・描画改善も得られる。ただし iOS IME の完全性は依然未確認で、mouse off 中の通常の選択・scroll と正しい report 遮断は公開 API だけでは証明できない。

## 判断の軸と暫定推奨

実質４案（xterm.js 6.0.0 をそのまま利用、ghostty-web 0.4.0、自前描画、xterm の parser・描画を維持して mouse / selection のみ自前）を (1) **DECSET の意味を保った mouse report と選択の分離、OSC 8 URI を含む出力の忠実性**、(2) iOS Safari / iPad PWA での変換位置と確定、(3) iframe 多 pane の資源・帯域・遅延、(4) leader の cols/rows を固定した content-fit、(5) daemon の state・WS 契約に必要な追加範囲で比較する。hterm は要件実証がなく、評価保留。自前描画の parser 一元化の利点と、daemon state が OSC 8 を持たない現状は同時に見る。中間案は xterm の既存描画・入力を生かす代わりに browser の parser と daemon の parser が並存する。単独 pane の描画速度や parser の言語だけで決めない。

**現時点では xterm.js 6.0.0 の DOM renderer を検証起点として維持する**。OSC 8 の live URI、mouse report、IME の cursor 同期、ESM と addon の経路を source で確認でき、現行 5.3.0 から具体的に移せる。ただし mouse off で選択・scroll を戻せるとの推奨ではない。中間案はその障害への局所的な候補だが、xterm は DECSET 中に内部 selection を disable するため独自 selection と event ownership が必要で、実機 PoC 前に「解決」とは言えない。自前描画は mouse / selection と fontSize を主体的に設計でき、daemon 正本から直接描けば browser と daemon の解釈差を取り除ける可能性がある。しかし現行 snapshot は色・OSC 8 URI・mouse mode を欠き、WS は cell 差分を配らず、IME・キーエンコード・scrollback まで新たな実装と契約が必要。今すぐ既存基盤の差し替えとして選べる段階ではない。ghostty-web 0.4.0 は OSC 8 URI が null、mouse report が未実装、IME 位置追従が未統合なので現要件を満たす版ではない。WebGL を全 pane の既定とするのは context-loss の報告と「多数 pane」が衝突する。

**xterm.js を確定採用した結論ではない**。最初の gate は 6.0.0 の一時ページで `?1000h` / `?1002h` / `?1003h` と `?1006h` の on/off、通常キー・`onBinary` と report の分離、off 時の drag 選択・copy・縦スクロール・カルーセルの touch を検証すること。xterm の DOM capture で report を止められても、内部 selection が使えなければ中間案の自前選択まで同じ PoC で検証する。それでも体験を成立させられない場合は、自前描画の前提となる daemon の色・OSC 8 URI・mouse mode 保持、WS の初期全量と差分・再同期、キーエンコードを先に設計・実測して再比較する。次に macOS 日本語 IME + iOS Safari / iPad PWA の日本語変換 (位置・確定・候補選択・重複なし)、8/16/24 pane × 可視/非表示の RAM・描画・ネットワーク bytes・入力から表示までの遅延、fontSize content-fit を同条件で測る。**新候補のブラウザ実機 PoC と iOS 実機試験、具体的な RAM/FPS/帯域・遅延の比較値は未実施・未計測**。推奨の再評価をその結果に依存させ、実測値を仮定しない。
